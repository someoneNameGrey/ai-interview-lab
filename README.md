# Grey Interview

A local browser and CLI training system for Grey's preparation for Backend SWE on AI teams,
Generative AI SWE, and Applied AI Engineer roles. Use the [revised roadmap](TRAINING.md) for the
24-week advanced path: production Python, evals, DeepSWE, and an Enterprise AI Support Agent.
The [course audit](COURSE_AUDIT.md) explains what was reused and which gaps the roadmap addresses.
The lab includes 32 lessons, 96 knowledge-check questions and 64 exercises, including the advanced
roadmap, both project reviews and a three-module DSA progression. Build projects in your own
development environment and submit evidence in the lab. Then try interview
questions generated by your local Codex CLI through the official Python SDK, or by Claude Code.
Your actual experience, prior answers, gaps and difficulty shape each interview session.

This is an independent practice simulator, not an employer's official process or a hiring predictor.
The default loop has six competency rounds with two turns each; change the tracks and turn count to
match a particular role. Model-scored answers are fallible practice feedback.

## Start the browser training workspace

Open PowerShell **in this project folder** and run:

```powershell
.\.venv\Scripts\grey.exe web
```

This opens **http://127.0.0.1:8765** and initializes local settings if needed. Keep the terminal
open while learning; Ctrl+C stops the server. Use `web --no-browser` to open the URL yourself,
or `web --port 8767` if the default port is occupied. Run this command instead of opening the
HTML file directly: the browser uses the local Python server for progress and model reviews.

1. Open **Learn** to begin with **Senior SWE diagnostic** or continue the recommended lesson.
   Phases and prerequisite links guide the path; optional refreshers remain available.
2. Take the **Knowledge check**. Answers are scored locally with explanations; pass at 80% (all
   three answers on the current short checks). You can revisit the guide and retake the check.
3. Select **Start exercises**. Coding answers use a code editor with syntax highlighting, line
   numbers, four-space indentation, bracket matching and undo. Put your explanation and tests in
   the separate **Reasoning & tests** box. Tab indents; Esc then Tab leaves the editor.
4. **Submit for review**, discuss feedback with the tutor, revise, and finish both exercises.
5. Open **Readiness** to see gaps per track, then **Practice** for fresh questions or a mock interview.

Use **Ask your tutor** in the bottom-right corner on any page. The chat stays open while you
navigate, remembers recent conversations, and uses the current lesson or exercise as context.
Ask follow-up questions, paste code, or request an example. Ctrl+Enter sends; Enter adds a line.
Minimize the panel to return to your work. Chat uses your configured provider and supports separate
`GREY_LLM_TUTOR_MODEL` and `GREY_LLM_TUTOR_EFFORT` overrides (including exercise coaching).
For Luna max, set these to `gpt-5.6-luna` and `max`, then restart the server. Leave them empty
to inherit the main model/effort. Question generation and answer review keep their own settings;
its history is saved locally. During practice, help counts as assisted; during mocks, only
requirement clarifications are available. The panel shows that mode before you send.

The required path has 19 applied/DSA modules plus six existing interview tutorials. Five foundation
refreshers and two ML reference modules are optional. Start DSA alongside project work with
`grey learn --lesson dsa-sequences`; its guides schedule two unaided sessions per week and progress
through sequences/search, trees/heaps/graphs, and basic dynamic programming. Exercises are original
LeetCode-style practice, not imported LeetCode problems.
System-design answers use a Markdown editor with **Mermaid diagram preview**. Code is reviewed by
the model; it is **not executed**. Run tests separately and include their results in your answer.

Guides, exercises and knowledge checks work without model calls. Generated interview questions,
tutor requests and answer reviews use your existing `.env` provider, model and effort settings.
Restart the server after changing `.env`. All browser libraries are bundled locally; normal use
does not require Node.js or a CDN.

Draft answers are saved in this browser; submitted answers, reviews, checks and sessions are saved
in `.grey/progress.sqlite3`. Use **Save & leave** and **Sessions** to resume. A failed review keeps
its submitted answer and offers **Retry review**. Unsaved drafts do not follow you to another browser.

Readiness is a practice recommendation: pass each required knowledge check for a core track, then earn at least
75 on each of its latest two unassisted first attempts, with no rubric dimension below 2 and no
low-confidence evaluation. Guided exercises and unfinished mocks do not count as independent
performance. Optional tracks use their own checks; refreshers do not block core readiness. You can
enter practice or a mock at any time; this is not a certification or hiring prediction.

## Start a training session in the CLI

Open PowerShell **in this project folder**. With the existing installation, run:

```powershell
.\.venv\Scripts\grey.exe learn
```

This opens the next required tutorial, starting with the senior diagnostic, or resumes your most recent unfinished
tutorial. You read a guide and worked example, attempt two exercises, then receive feedback from
the model configured in `.env`. Tutorials are guided practice, not mock interviews.

Choose a topic or browse the lessons:

```powershell
.\.venv\Scripts\grey.exe learn --list
.\.venv\Scripts\grey.exe learn --lesson system-design
.\.venv\Scripts\grey.exe guide system-design
```

`guide` and `learn --list` work offline, even before `init`. Reading the lesson and opening its
exercises do not call a model. Feedback, hints and tutor explanations use your selected account's
quota. The system-design guide includes a Mermaid example; diagrams are submitted as text in a
Markdown file and are not rendered in the terminal.

### During a tutorial

| At the prompt | What it does |
| --- | --- |
| Press Enter | Type an answer; finish with `.done` on its own line |
| `file C:\path\to\answer.md` | Submit a code/design answer from a file |
| `guide` | Read the current lesson again |
| `explain TOPIC` | Ask the tutor to explain a concept with an example |
| `hint` | Get a nudge for the current exercise |
| `clarify QUESTION` | Ask about the exercise requirements |
| `pause` | Leave the tutorial with submitted work saved |

After feedback, press Enter to continue, choose `retry` to revise, or use `review QUESTION` to ask
about the feedback. Both exercises must be reviewed before the tutorial is marked complete.
Completion records practice, not mastery; tutorial scores do not affect independent interview
difficulty or readiness statistics. There is no required passing score.

### Resume, repeat, or retry a failed review

```powershell
.\.venv\Scripts\grey.exe learn
# Or use the session ID printed when you started:
.\.venv\Scripts\grey.exe learn SESSION_ID
.\.venv\Scripts\grey.exe sessions

# Repeat a lesson from the beginning:
.\.venv\Scripts\grey.exe learn --lesson coding --new

# Your answer is saved before model review. Retry a failed review:
.\.venv\Scripts\grey.exe grade SESSION_ID

# Revise from a file before finishing the tutorial:
.\.venv\Scripts\grey.exe answer SESSION_ID --file .\improved-answer.md --revise
```

The advanced lessons cover Python, evals, agents, sandboxing, reliability, observability, retrieval,
enterprise security, architecture, both projects, customer cases, communication and DSA. The six
interview tracks remain coding, system design, AI systems, project, debugging and behavioral.
Post-training and research-engineering are optional. After finishing a
tutorial, run `learn` again for the next one. Check the map with `learn --list` or `progress`.

When you want fresh interview questions, use:

```powershell
.\.venv\Scripts\grey.exe run --tracks coding system-design --turns 2
# Full mock: no hints, and feedback stays hidden until completion.
.\.venv\Scripts\grey.exe run --mode mock
```

## First-time setup (Windows PowerShell)

Open a terminal **in this project folder**. Requires Python 3.10+ and a signed-in Codex CLI.
The SDK can also use its bundled Codex runtime when `codex` is not on PATH.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
codex login
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
.\.venv\Scripts\grey.exe init
.\.venv\Scripts\grey.exe doctor
.\.venv\Scripts\grey.exe doctor --live
.\.venv\Scripts\grey.exe learn
```

These commands do not require PowerShell script activation. If you activate the environment or put its
Scripts directory on PATH, use `grey` directly as in the examples below. On macOS/Linux, create the
environment with `python3 -m venv .venv`, activate with `source .venv/bin/activate`, then run the same
`python -m pip ...` and `grey` commands. Copy `.env.example` to `.env` with `cp` on macOS/Linux.

The app loads `.env` from the current working directory. Existing shell variables take precedence.
`.env` is gitignored. Codex and Claude use their local CLI authentication; no OpenAI API key is
required for those modes. Model inference still runs with the provider and consumes your account's
quota. `doctor` is offline; `doctor --live` sends one small generation request.

## Switch providers and models

Edit `.env` and run the next command:

```dotenv
GREY_LLM_PROVIDER=codex
GREY_LLM_MODEL=gpt-5.5
GREY_LLM_EVALUATOR_MODEL=
```

For Claude Code, install its CLI, run `claude auth login`, then use:

```dotenv
GREY_LLM_PROVIDER=claude
GREY_LLM_MODEL=sonnet
GREY_LLM_EVALUATOR_MODEL=opus
```

`GREY_LLM_MODEL` controls questions and coaching. `GREY_LLM_EVALUATOR_MODEL` optionally selects a
separate answer-review model. Any model ID available to your chosen CLI/account is accepted; there
is no silent model fallback. To use the CLI's configured default, leave both model variables blank
and set `model` / `evaluator_model` to `null` in `.grey/config.json` if previously customized.
The supplied Codex example uses `gpt-5.5`, verified locally. The existing local CLI rejected its
configured `gpt-6-astra` default as requiring a newer CLI; upgrade Codex before selecting that model.

PowerShell overrides work without editing files:

```powershell
$env:GREY_LLM_PROVIDER = "claude"
$env:GREY_LLM_MODEL = "sonnet"
$env:GREY_LLM_EVALUATOR_MODEL = "opus"
grey doctor --live
```

Switch both provider and model together when moving between model families. Remove shell overrides
with `Remove-Item Env:GREY_LLM_PROVIDER` (and the corresponding model variables) to use `.env` again.
On macOS/Linux, use `export GREY_LLM_PROVIDER=claude` and the same variable names.

| Setting | Behavior |
| --- | --- |
| `GREY_LLM_PROVIDER` | `codex` (default), `claude`, or `openai` |
| `GREY_LLM_MODEL` | Question/coaching model; also review model unless overridden |
| `GREY_LLM_EVALUATOR_MODEL` | Optional separate review model |
| `GREY_LLM_EFFORT` | Question/coaching effort; reviews inherit it |
| `GREY_LLM_EVALUATOR_EFFORT` | Optional separate review effort |
| `GREY_CODEX_BIN` | Optional Codex executable path; otherwise PATH, then bundled runtime |
| `GREY_CLAUDE_BIN` | Optional Claude executable path; otherwise `claude` on PATH |

Set effort in `.env`, for example:

```dotenv
GREY_LLM_EFFORT=medium
GREY_LLM_EVALUATOR_EFFORT=high
```

The main effort defaults to `medium` in the supplied `.env`. Leave the review effort blank to
inherit the main effort. Without an explicit effort in the environment or config, the runtime
uses its own default. Config fields are `effort` and `evaluator_effort`; explicit environment
settings override saved sessions too. Setting the main effort resets the review effort to inherit
unless a review environment override is also supplied. A provider switch clears saved efforts.
`grey doctor` displays both selections; call metadata records the requested effort (`null` means
provider default). Effort does not change the selected model.

Recognized levels are `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`, and `ultra`.
Availability depends on the selected provider, model and CLI version; unsupported combinations
fail without silently downgrading. Claude CLI accepts `low`, `medium`, `high`, `xhigh`, and `max`.

The original Responses API remains available with `GREY_LLM_PROVIDER=openai`, an accessible model
in `GREY_LLM_MODEL`, and `OPENAI_API_KEY`. Only this backend uses `max_output_tokens`; the local CLI
backends use their own output limits. `timeout_seconds` applies to all backends.

Edit `.grey/config.json` after `init` to add your actual technologies, experience and project context.
Only Grey's name, software-engineering background and target role are prefilled. Configuration is
validated and snapshotted per session; config-file edits affect **new** sessions. Explicit provider
and model environment overrides also apply to **resumed** sessions, allowing you to retry a saved
answer with a different model. Changing provider clears saved model choices unless environment
models are also supplied; setting the main model makes reviews inherit it unless a review override
is supplied. Each successful call records its provider, model selection, response ID and usage.
When a CLI default is used, metadata says `codex-default` or `claude-default`, not a resolved model ID.

Use `--home PATH` before a command or `GREY_HOME` to share progress across working directories.
The default `.grey` is relative to the current working directory. `.env` remains relative to the
working directory even when `--home` points elsewhere.

## Your first session

```powershell
grey run --tracks coding ai-systems --turns 2
```

The interactive interviewer prints one question at a time. Press Enter to write a multiline answer;
enter `.done` on a separate line to submit. Use `file PATH` for code or a longer written answer. Use
`hint`, `clarify TEXT`, or `pause` at the action prompt. `.cancel` cancels multiline input. The printed
session ID lets you resume with `grey run SESSION_ID`. Sessions, questions, answers and feedback survive
restarts. Text not yet submitted is not saved.

Questions show a suggested time budget; elapsed wall time is recorded but not used as a score penalty
(it includes breaks). You control pacing. The interviewer is instructed not to execute candidate or generated code. Codex runs in a
read-only sandbox with escalation denied; Claude runs without tools or MCP servers. Run
your own tests in your chosen development environment, then include the code, explanation and relevant
test output in your answer. Evaluation labels this output as self-reported evidence.

Use individual commands when you want to work in your editor, revise, or script the workflow:

```powershell
grey start --mode practice --tracks coding ai-systems --turns 2
# Copy the printed ID in place of SESSION_ID below.
grey next SESSION_ID
grey clarify SESSION_ID "Are duplicate job IDs possible?"
grey answer SESSION_ID --file .\my-answer.md
grey review SESSION_ID "Explain the verification gap in my answer."
grey answer SESSION_ID --file .\improved-answer.md --revise
grey next SESSION_ID --remediate
# Repeat next + answer for the scheduled turns, then:
grey finish SESSION_ID
grey progress
grey export SESSION_ID --out .\report.md
grey export SESSION_ID --format json --out .\transcript.json
```

The clarification above is an example of a CLI argument, not a bank of training questions. Use a
clarification relevant to your actual generated task. Exports never overwrite an existing file.
Markdown exports contain feedback; JSON exports include full transcripts, call metadata and private
interviewer notes. Neither is encrypted. `grey show SESSION_ID` redisplays the current public question;
`grey sessions` lists your IDs; `grey report SESSION_ID` shows feedback so far.

Full default mock:

```powershell
grey run --mode mock
```

Mock mode permits requirement clarifications but no hints or revisions. Scores, lessons and exports
remain hidden until all turns are graded and the session is finished. Interactive mode finishes
automatically; individual-command mode requires `grey finish SESSION_ID`. The local database is
user-owned, so this is a learning boundary, not a tamper-proof examination system.

## Scoring and adaptation

Four equally weighted dimensions score 0–4: correctness, reasoning, verification, communication. The
overall percentage is `round(sum / 16 * 100)`. Every dimension requires evidence and an improvement.
Anchors: 0 absent/incorrect; 1 major gaps; 2 partially sound with material omissions; 3 sound with
minor omissions; 4 precise, robust and justified. Technical and behavioral interpretations differ in
the evaluator prompt. Scores are not probabilities of being hired.

An unassisted first attempt scoring at least 80 moves the track up one level; below 50 moves it down
one; otherwise it stays. Levels are bounded 1–5. Low-confidence evaluations do not change difficulty.
Hints and revisions are marked assisted and do not raise the baseline. New sessions initialize each
track by replaying its last three unassisted first-attempt evaluations from the configured starting
level. The progress view averages the last five such attempts and excludes unfinished mocks. It does
not imply that different generated questions are psychometrically equivalent.

Follow-ups receive the previous answer, feedback and competency; first questions receive recent gaps.
`next --remediate` explicitly requests gap-focused practice. Exact duplicate prompts are rejected;
semantic variation is guided by prompts and recent titles, not guaranteed by a similarity classifier.
Revisions preserve the original answer and grade. Lessons and exercises follow each practice attempt.
See [TRAINING.md](TRAINING.md) for phase dependencies, exercises, interview/work disciplines and the
DeepSWE and Enterprise AI Support Agent portfolio projects.

## Reliability, data and cost

- SQLite atomically stores session snapshots and rejects conflicting concurrent writes. Answers are
  committed before grading. If grading fails, use `grey grade SESSION_ID`; do not resubmit the answer.
- A failed question request leaves the session position unchanged. Retry `next`. A pending question is
  redisplayed without another generation call. Timeouts are configurable. The OpenAI API adapter permits at most two SDK retries; local
  runtimes may apply their own internal retries.
- Refusals, incomplete responses, malformed structures and duplicate rubric dimensions fail clearly.
  For API output exhaustion, raise `max_output_tokens` before starting a new session. For local
  CLI failures, check CLI/model compatibility, login, quota and timeout.
- Profiles, recent relevant history, submitted answers and coaching requests go to the selected
  provider. API mode uses `store=False`; Codex uses ephemeral threads and Claude disables session
  persistence. These settings do not override provider retention policies. Do not include
  employer secrets. State is plaintext in `.grey/progress.sqlite3`; keys are never stored there.
- Usually one call generates a question and one grades an answer. Coaching and revisions add calls.
  The API output token limit does not bound total spend; local CLI output limits are runtime-managed. `grey progress` shows recorded successful calls
  and tokens, not a billing statement: failed, interrupted, conflicting or rejected-result requests,
  SDK retries and `doctor --live` may incur usage not recorded in sessions. Configure account spend
  controls separately. No background agent or scheduled calls run.

## Development and validation

```powershell
python -m pip install -e ".[dev]"
python -m pytest
python -m ruff check .

# Only when changing frontend JavaScript/dependencies (Node.js required):
npm ci
npm run build
```

Tests use temporary databases, mocked local runtimes, and an in-memory HTTP transport through the
OpenAI SDK. No login or network access is needed. Coverage includes question/review model routing,
provider switching, `.env` precedence, SDK signatures, structured outputs, timeouts, cleanup, resume,
mock feedback boundaries, adaptation and CLI exports.

`requirements-dev.lock` records the tested dependency versions. Reproduce them with
`python -m pip install -e ".[dev]" -c requirements-dev.lock`.

Validation: **134 tests passed**, Ruff passed and browser assets rebuilt. Coverage includes all 32
lesson lifecycles, advanced readiness, legacy progress, browser APIs, checkpoint persistence,
mock feedback boundaries, saved-answer recovery, tutor context, offline guides and CLI resume behavior.
In the earlier live provider check, Codex `gpt-5.5` returned structured coaching,
generated a coding question, reviewed a synthetic answer across all four rubric dimensions, and
completed the saved interview session. Claude's local OAuth session was expired and could not
refresh; run `claude auth login` before a live test.
An installed CLI or an offline `doctor` success does not establish working authentication.

Structure: `cli.py` handles the interface and `.env` loading; `engine.py` controls sessions and
adaptation; `curriculum.py` loads the guides and exercises in `curriculum/`; `store.py` owns
persistence; `provider.py` integrates Codex, Claude and the optional
OpenAI API; `models.py` defines validated schemas and model selection; `prompts/` holds editable
interviewer, evaluator and coaching instructions. `web.py` serves the local browser API;
`web/app.js` is the frontend source; `static/` contains the HTML, CSS and bundled assets.
The CLI can still be used without starting the web server.
